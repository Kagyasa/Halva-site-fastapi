# Halva

Сайт кафе-кондитерской: FastAPI, PostgreSQL, SQLAdmin и обычные HTML/CSS/JS.
Python 3.12; для работы сайта Node.js не требуется. Node 22+ нужен только для проверок JavaScript.

## Локальный запуск

Из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
python -m app.cli generate-secret
```

Впишите полученный ключ в `ADMIN_SECRET_KEY` внутри `.env`. Укажите параметры вашей
PostgreSQL в `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.
Существующий `.env` можно сохранить: прежние имена переменных поддерживаются.
Локально оставьте `APP_ENV=development` и `ADMIN_SESSION_HTTPS_ONLY=false`.

Если PostgreSQL ещё нет, можно установить Docker Desktop и запустить только базу:

```powershell
docker compose up -d db
```

Параметры базы берутся из `.env`. Если порт 5432 уже занят вашей PostgreSQL,
используйте имеющуюся базу. Для новой базы нужны созданные пользователь и база с именами из `.env`.
На Linux/macOS активация окружения: `source .venv/bin/activate`, копирование: `cp .env.example .env`.

```powershell
python -m alembic upgrade head
python -m app.cli create-admin --username admin --role admin
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Пароль вводится интерактивно, минимум 12 символов. Сайт: <http://127.0.0.1:8000>,
админка: <http://127.0.0.1:8000/admin>. Для сотрудника:
`python -m app.cli create-admin --username employee --role staff`.
Для явной смены пароля/роли существующего пользователя добавьте `--update`.

Сотрудники видят все заявки, кроме выполненных и отменённых, независимо от возраста.
Администраторы видят все статусы за последние два календарных месяца **по времени создания**.
Правило действует для списка, поиска, экспорта, деталей и редактирования.
Заявки старше двух месяцев остаются в базе: фильтр не удаляет их.

## Юридические документы

Готовых документов в репозитории нет. Старые заглушки не публикуются и не открывают
приём заявок. Сайт, каталог, витрины и админка работают; форма объясняет, почему отправка недоступна.

Когда готовые тексты появятся, сохраните их в двух файлах UTF-8 и выполните:

```powershell
python -m app.cli publish-legal --policy-file policy.txt --policy-version 2.0 --consent-file consent.txt --consent-version 2.0 --confirm-final
```

Версия `2.0` в примере избегает конфликта с прежней заглушкой `1.0`. При изменении
документа используйте новую версию. Опубликованный текст нельзя подменить: сохраняются
его контрольная сумма и история согласий. Форма отправляет ID именно тех версий,
которые загружены для ознакомления; при смене документов нужно подтвердить согласие снова.
`seed_legal_documents.py` оставлен как совместимая точка входа с теми же аргументами.

## Почта и надёжность заявок

Заполните SMTP-переменные и `ORDERS_EMAIL` в `.env`:

- Порт 587: `SMTP_STARTTLS=true`, `SMTP_USE_SSL=false`.
- Порт 465: `SMTP_USE_SSL=true`, `SMTP_STARTTLS=false`.
- `EMAIL_WORKER_ENABLED=true` включает обработчик очереди вместе с сервером.

После изменения `.env` перезапустите сервер. Сертификат SMTP проверяется.
Заказ, позиции, согласие и письмо в очереди сохраняются одной транзакцией.
Ошибки почты не теряют заявки: повторные попытки выполняются через 30 секунд,
затем с растущей задержкой до часа. После перезапуска очередь продолжается.
Статусы доступны в админке в разделе «Почтовые уведомления».

Альтернатива встроенному обработчику: оставить `EMAIL_WORKER_ENABLED=false` и запустить
`python -m app.cli email-worker` во втором терминале. Для одной попытки: `--once`.
Не используйте оба способа без необходимости. Приём заявок с выключенным обработчиком
возможен, но письма останутся в очереди до его запуска.

Браузер сохраняет ключ попытки отправки, чтобы повторный запрос после сетевого сбоя
вернул уже созданную заявку. Цена и доставка считаются сервером с точностью до копейки;
если цены изменились, клиент получает новую сумму для повторного подтверждения.
Отправка SMTP имеет семантику «как минимум один раз»: при аварии после принятия письма
SMTP-сервером, до отметки в базе, возможен повтор письма. Номер заявки и Message-ID
позволяют распознать такой повтор; сама заявка повторно не создаётся.

## Данные и обновление существующей базы

Перед обновлением сделайте резервную копию PostgreSQL. Применение:

```powershell
python -m alembic upgrade head
```

Порядок применения патча и обновления работающей локальной установки описан
в [инструкции обновления](docs/update-existing-installation.md).

Новая миграция добавляет очередь, ключи повторных запросов, индексы, часы работы точек,
проверки цен/количеств/диапазонов и уникальность slug и позиции витрины.
Старые времена каталога переводятся из UTC без часового пояса в UTC с часовым поясом.
Если в базе есть отрицательные цены, некорректные диапазоны или дубли, миграция
останавливается **до изменений**, сообщает таблицу и ID. Исправьте эти записи через
старую админку и повторите миграцию. Автоматического удаления данных нет.

```powershell
python seed_site_contacts.py
python fill_display_names.py
python fill_vk_urls.py
```

Эти команды заполняют недостающие данные. Существующие контакты, включая TG и MAX,
сохраняются. Скрипты названий/VK заменяют заполненные значения только с `--overwrite`.
Цены берутся из каталога; телефоны, адреса и часы работы — из раздела «Точки».
Старые изображения сохранены, поскольку ссылки на них могут храниться в вашей базе.

Импорт старого каталога Django (целевая база должна быть пустой):

```powershell
python migrate_from_django.py "C:\path\to\old\db.sqlite3"
```

Источник открывается только для чтения; перенос всех таблиц выполняется одной транзакцией.
Заявки и пользователи админки этим скриптом не импортируются.

## Проверки

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m ruff check .
npm ci --ignore-scripts
npm test
```

По умолчанию тесты используют временную SQLite. Для PostgreSQL задайте
`TEST_DATABASE_URL` на тестовую базу: каждый тест создаёт и удаляет только собственную
случайную схему. GitHub Actions проверяет PostgreSQL 16, миграции, Python, поведение формы в DOM
и Chromium на ширинах телефона, планшета и компьютера. Для браузерных проверок
локально: `npx playwright install chromium`, запуск тестового сервера на 8765
и `npm run test:browser`. DOM-проверки не заменяют визуальную проверку сайта.

На сервере используйте один процесс Uvicorn (`--workers 1`) и одну реплику приложения:
ограничители частоты запросов пока хранятся в памяти процесса. Для нескольких процессов
понадобится общий ограничитель в Redis или базе. Очередь писем использует блокировки PostgreSQL.

Размещение описано в [инструкции для Timeweb](docs/deployment-timeweb.md).
